3. Top 3 Performance Bottlenecks & Safe Remediation Plan (Phase 11)

Bottleneck #1 (CRITICAL): Per-IP Rate Limiters Reject 85%–95% of 200 College Lab / Campus Wi-Fi Users

Affected File: backend/src/app.js (lines 108–186)

Root Cause: participantAccessCodeLimiter (15/10min), participantRegisterLimiter (10/15min), submissionLimiter (30/1min), and participantLimiter (600/5min) key solely by req.ip. When 200 students in a college venue share a public NAT IP, 185/200 logins and 170/200 submissions fail with HTTP 429.

Smallest Safe Fix: Key authenticated limiters by participant session token/ID, key login/registration limiters by composite (req.ip + accessCode/rollNumber), and raise per-IP ceilings to accommodate 200+ users on campus NAT.

Bottleneck #2 (CRITICAL): 50 Sequential SQL INSERT Round-Trips per Submission Transaction

Affected Files: backend/src/routes.js (lines 987–1015) & backend/src/db.js (lines 16–25)

Root Cause: POST /api/attempts/:attemptId/submit loops over all 50 questions and executes 50 sequential await client.query('INSERT INTO answers ...') statements inside a FOR UPDATE transaction. At 68.45ms RTT per query to Neon Singapore, each user holds a pooled connection for ~3.83 seconds (11,200 sequential queries for 200 users across a 10-connection pool).

Smallest Safe Fix: Replace the 50-query loop with a single parameterized INSERT INTO answers ... SELECT $1, u.qid, u.opt FROM UNNEST($2::bigint[], $3::int[]) AS u(qid, opt) ON CONFLICT DO UPDATE query (collapsing 50 round-trips into 1) and raise pg.Pool max connections from 10 to 25.

Bottleneck #3 (HIGH): 270 req/s Uncached Background Polling & Unindexed audit_events Scans

Affected Files: backend/src/routes.js (lines 79–85, 654–703, 735–744), src/components/BroadcastNotification.tsx, backend/migrations/

Root Cause: Every browser runs 4 polling timers (including duplicate 3s polls to /api/competition/state in App.tsx and BroadcastNotification.tsx), generating ~270 req/s (~540 SQL queries/sec) for 200 users. Neither /competition/state nor /rounds/:id/questions is cached in memory, and audit_events lacks an index on event_type (1,016,121 sequential tuple reads recorded).

Smallest Safe Fix: Add a 1.5s TTL in-memory cache for /api/competition/state and qualification maps (invalidated on admin state/broadcast mutations), a 30s TTL cache for /api/rounds/:id/questions, and create index idx_audit_events_type_id ON audit_events(event_type, id DESC).
